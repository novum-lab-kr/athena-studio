# Athena — 프론트·백엔드 멀티 레포 작업 워크스페이스

여러 레포를 한 곳에서 작업하는 워크스페이스의 **도구 무관 공통 규칙**이다 — Claude Code · Codex · 그 밖의 에이전트가 모두 여기서 출발한다. Claude Code 아테나(팀 리드)는 `CLAUDE.md` 가 더한다. 위임 기능이 없는 도구(Codex 등)는 아테나 역할 없이 **직접** 작업하되 이 규칙과 지식을 그대로 따른다.
여기에는 매 작업 지킬 것만 둔다. 자세한 절차는 "**읽을 때**" 와 함께 `docs/` 를 가리킨다 — 그때가 오면 그 문서를 읽는다.

## 1. 담당 레포와 기준 브랜치

- 담당 레포 · 에이전트 · 라우팅은 팩에 있다 — **`pack/ROUTING.md`**(기계 정본 팩 `pack.json`). 경로는 어디서나 `repos/<레포>`(`scripts/setup.sh` 가 링크) · 팩 파일은 `athena pack link` 가 코어 자리(`.claude/agents` · `docs/knowledge/<레포>` · `scripts/verify/<레포>.sh` …)에 링크로 건다
- **기준 브랜치(`pack.json` `branch`) = 운영 반영분.** 문서 · 지식은 이 브랜치를 읽어 만든 것이라 로컬이 뒤처져 코드와 다르면 **문서 오류가 아니다.** 작업 전 `git status --short --branch` 로 차이를 보고 보고에 적는다. 작업 브랜치 base 는 `prBase`
- **범위 밖** = 팩 표에 없는 레포. 변경이 필요하면 멈추고 사용자에게 알린다
- 계획서 · 이슈는 본체 기준 논리 경로(`plans/…md`)로 다루고 실제 경로로 풀지 않는다

<!-- lead-only -->
- **여러 팩 구조**(본체에 `.pack-data`)면 팩마다 본체가 따로다. 아테나 세션은 본체에서만(데이터 폴더에서는 켜지 않는다) · 설치본(`~/.athena-studio/core` · `bodies/`)은 고치지 않고 코어 정비는 코어 정본 레포에서 브랜치 · PR 로(`CLAUDE.md` 갈래 표). 다른 팩 열기 · 업데이트 · 가져오기는 그때 `docs/pack.md` "여러 팩"

### 어느 레포인지 고르기
- 팩 `ROUTING.md` "어느 레포인지 고르기" 를 따른다. 해석이 둘 이상이면(같은 이름의 화면이 여러 레포에 있는 등) **반드시 사용자에게 확인**한다
- **프론트와 백엔드가 함께 바뀌면 백엔드 먼저** — 공유 패키지 먼저와 같은 규칙. 계획서 공통 스펙에 엔드포인트 · 요청 · 응답 형식을 적고, 백엔드 에이전트가 보고한 "계약 변경"을 프론트 에이전트에 넘긴다

## 2. 무엇을 읽고 시작할 것인가

### 2.1 규칙은 세 층 — 충돌하면 뒤가 우선
팀 공통 `docs/knowledge/common/`(`coding` · `git` · `reporting` · `verify` · `learning`) → 레포 규칙 `docs/knowledge/<레포>/rules.md`(공통과 다른 점 · 고유 규칙) → 레포 원문(레포 안 `CLAUDE.md` · `.ai/*.md` · `README.md` 등). 레포 원문이 코드와 다르면 **코드를 우선**하고 차이를 보고한다.

### 2.2 항상 읽는 것 (작업 크기와 무관)
knowledge 전체를 미리 읽지 않는다. 대신 아래는 작업이 아무리 작아도 예외 없이 적용된다.
- 5절 **작업 규칙**
- 대상 레포 `rules.md` 의 **"필수" 절** · `gotchas.md` **전체**(함정은 어느 작업에서 밟을지 모른다). 공책이 나뉘어 `gotchas/<폴더>.md` 가 있으면 작업할 파일이 그 폴더 안일 때 그 화면 파일도 전부(작업이 다른 폴더로 넓어지면 그 파일도 · `learning.md` 7절)
- 대상 repo/app/worktree 확인(`git status --short --branch`) · 아테나 **자체** 작업(`repo: athena`)이면 `docs/knowledge/athena/gotchas.md`
- `docs/knowledge/**` 는 자동으로 실리지 않는다 — 직접 읽는다. 코드 규칙 요약은 Claude Code 에 자동으로 실리고, 그렇지 않은 도구(Codex 등)는 `docs/knowledge/common/coding.md` 를 직접 읽는다. 무엇이 자동으로 실리는지 · 읽는 법은 헷갈릴 때 `docs/knowledge/common/context.md`

### 2.3 그다음은 작업 유형에 따라 필요한 절만
| 작업 유형 | 추가로 읽을 것 |
|---|---|
| 문구 · 스타일 국소 수정 | 대상 파일과 인접 사용처 |
| 새 화면 · 기능 | 해당 `workflows.md` 절 → `patterns.md` 가 가리키는 **실제 파일** → `structure.md` 라우트 · 권한 표 |
| API · 폼 · 상태 변경 | 해당 API/폼 pattern, 타입 · 생성 설정, `rules.md` API 절 |
| 버그 수정 | 재현 근거, 관련 코드 · 테스트(과거 이유가 필요할 때만 History) |
| 구조 변경 · 공유 패키지 | `structure.md` 와 소비처, 해당 workflow, 담당 범위 · 영향 규칙 |
| 기존 작업 재개 | 해당 plan 의 **Checkpoint**, 현재 diff · worktree(2.6) |

새 구현에서 workflow 와 대표 코드 확인을 생략하지 않는다(국소 수정만 면제). 범위가 커지면(문구 → 새 화면) 다시 고른다. 링크를 적어 둔 것은 읽은 것이 아니다.

### 2.4 무엇을 믿을 것인가
- **지시** = 상위 지시 · 현재 사용자 요청 · 승인된 계획 범위 / **현재 구현 사실** = 대상 트리의 코드 · 설정 · 검증 결과(그다음 레포 원문, 그다음 출처 있는 knowledge) / **진행 상태** = 계획서("완료" 기재는 diff · 검증으로 확인) / **Memory · History · 대화 요약** = 어디를 볼지 찾는 단서일 뿐 근거가 아니다
- "코드가 우선"은 현재 구현을 판단하는 원칙이다 — 요구사항 · 권한 · 보안 규칙을 무효화하지 않는다. **어디서도 확인되지 않는 것은 근거가 아니다**(5절 추측 금지)
- 작업 브랜치 코드와 운영 기준 브랜치는 다른 범위다 — 차이는 두 ref 와 경로를 기록하고, 작업 브랜치의 임시 구현을 운영 knowledge 에 덮어쓰지 않는다. 표 전문은 `context.md` "근거"

### 2.5 Memory와 History
Memory 에는 프로젝트가 바뀌어도 유효한 워크스페이스 운영 규칙만 — 버전 · 경로 · 진행 단계 · 현재 작업 · 브랜치 · 완료 여부 · 구현 결정은 "오래 쓸 것 같아도" 넣지 않는다(계획서 · knowledge 몫). History(과거 세션)는 코드 · 계획서로 답할 수 없는 **과거 이유**가 필요할 때만 찾고, 현재 사실이나 실행 권한으로 쓰지 않는다 — 찾을 때 `context.md` "Memory와 History" 를 읽는다.

### 2.6 작업 재개 (`/new` · 대화 압축 이후)
진행 상황은 **해당 plan 의 Checkpoint** 에 있다.
1. 지정된 plan 하나를 읽는다. 지정이 없으면 관련 서비스의 진행 중 plan 후보만 좁히고, 구분이 안 되면 사용자에게 묻는다
2. repo/app/worktree 와 현재 diff 를 확인한다. Checkpoint 의 `Work ref` 와 다르면 그 차이를 먼저 평가한다
3. `Next` 가 **현재 코드에서도 유효한지** 확인하고 진행한다
4. 바뀐 ref 에서 과거 검증 결과를 현재 통과로 재사용하지 않는다

Checkpoint 는 단계 완료 · 차단 변화 · 리뷰 반영 · 세션 종료(`/new`) 직전에 갱신한다(매 턴 X · 여러 에이전트면 각자 보고하고 **팀리드가 취합**). 압축 훅(`compact-checkpoint.py`)이 남기는 `- Auto snapshot:` 은 기계 상태일 뿐 Progress · Next 를 대신하지 않는다(동작 `context.md` "대화 압축").

## 3. 레포 지식 베이스
`docs/knowledge/<레포>/`(모노레포는 `<레포>/<앱>/`) — `structure.md`(디렉토리 · 라우트 · 스크립트 맵) · `patterns.md`("이런 걸 만들 땐 이 파일을 따라라") · `workflows.md`(반복 작업 체크리스트) · `gotchas.md`(함정 · 이력 · 문서와 코드 불일치 · 설치만 되고 안 쓰는 라이브러리). 레포마다 관례가 달라 다른 레포의 패턴을 가져오지 않는다. `.claude/agents/<이름>.md` 는 역할 · 담당 범위 · 지식 진입점이지 기술 사실의 정본이 아니다(frontmatter 는 Claude 전용 · 본문은 도구 무관).

## 4. 검증
에이전트와 리뷰어가 **같은 스크립트**로 검증하고 그 출력 표를 그대로 붙인다.
```bash
scripts/verify/<레포>.sh [<앱|패키지…>]          # 에이전트 — 목록 · 인자는 pack/ROUTING.md "검증 스크립트"
scripts/verify/reuse.sh <레포> [<앱|패키지…>]    # 리뷰어 · commit.sh — 같은 트리로 이미 통과했으면 ♻️ 재사용
```
워크트리는 `ATHENA_VERIFY_DIR=<워크트리>` 를 붙인다(없으면 메인 체크아웃을 검증한다). Node 버전(`.nvmrc`) · 생성물이 없으면 타입 검사 건너뜀 · 재사용 열쇠 · `⏭ 건너뜀(규칙)` 은 실행 전 · 결과가 이상할 때 `docs/knowledge/common/verify.md`. **실행하지 못한 검증을 통과한 것처럼 보고하지 않는다.**

## 5. 작업 규칙 (작업 종류와 무관하게 항상)

- **바꾸는 작업은 모두 계획서 하나에 묶인다** — 예외 없음. 사용자가 정할 것이 있거나 여러 레포 · 담당을 맞춰야 하면 정식(`docs/plan-template.md` md + 같은 이름 html 결정 콘솔 — [이대로 진행] 으로 확정, 확정값은 md · html 에), 아니면 경량(`plans/task/…md` — `node scripts/new-plan.mjs`). 같은 작업의 추가 요청은 그 계획서에 이어 쌓고, 아무것도 바꾸지 않는 질문 · 설명에는 만들지 않는다. 사용자가 "바로 고쳐"라고 하면 경량으로 바로 하되 보고에 적는다. 시작할 때 한 줄로 알리고(`📋 경량으로 진행합니다 — 이유 · 경로`) 끝나면 Checkpoint(Status · Progress · Validation)를 채운다
- **새 작업 브랜치에서 시작한다** — `prBase`(개발 브랜치 · 문서 기준 `branch` 와 다르다)에서 딴 **워크트리**가 기본이라 메인 체크아웃을 건드리지 않는다. 지금 브랜치에 얹지 않고, 남의 미커밋 변경을 stash 하지 않는다(절차 `git.md` "작업 브랜치 만들기"). 예외 — **main 직접 레포**(`"direct": true`): 메인 체크아웃의 `prBase` 에서 바로 작업하고(시작 전에 그 브랜치 · 최신인지 확인) "올려줘" 는 `ship.sh` 의 빨리 감기 push(`docs/pack.md`)
- **담당 범위 밖은 수정하지 않는다** — 멈추고 보고한다(다른 레포 · 공유 패키지는 아테나에). 요청이 여러 레포 · API · 구조 변경으로 커지면 멈추고 알린다(정식 계획서 — 아테나)
- **버그 수정**은 계획서에 재현 조건 · 기대 동작 · 실제 동작을 먼저 적는다. 고치기 전에 재현 테스트나 재현 절차로 실패를 확인하고(자동 테스트 강제 아님) 고친 뒤 같은 방법으로 다시 확인해 전 · 후를 남긴다. 재현 못 했으면 확보한 근거와 미확인을 나눠 적고 원인을 확정하지 않는다 — 미확인 · 실행 불가를 통과로 보고하지 않는다. 원인이 프론트 밖(API 응답 · 공유 패키지)이면 알린다
- 해석이 여러 개면 기존 코드 · 설정 · 승인된 결정으로 먼저 좁힌다. 범위 · 사용자 동작 · 데이터 · 권한 · 외부 계약이 달라지는 해석이 남으면 선택지 · 영향 · 추천안으로 확인받는다(그 결정에 기대지 않는 작업은 계속 · 아테나의 디스패치는 확정 뒤)
- **추측으로 개발하지 않는다.** 코드만 보고는 알 수 없는 사실 — 외부 계약(API 응답 모양 · 필드 · 키 이름 · 에러 코드) · 제품 정책 · 기본 동작 · 데이터의 뜻 — 은 근거(2.4 — 지금 코드 · 실행 · 검증 결과, 출처를 확인한 원문 · 문서, 사용자 말, 승인된 계획서)가 있을 때만 코드에 넣는다. 없으면 먼저 코드를 읽고 · 돌려 보고 · 문서를 확인하고, 그래도 모르면 그 부분만 멈추고(기대지 않는 작업은 계속) 계획서 Blocked 에 적은 뒤 **모르는 것을 모아 한 번에** 묻는다 — 항목마다 무엇을 모르는지 · 어디까지 확인했는지 · 확인에 필요한 것 · 추천안. 물을 때 **요청을 연다**(`bin/athena request open --kind question …` — "확인 필요" 는 이것만 센다 · 대화로 답을 받으면 `request answer <id> --by chat`, `[요청 <id>]` 가 pane 으로 오면 받자마자 `request ack <id>` · `docs/requests.md`). 더 할 일이 없으면 Status `blocked`. 그럴듯한 임시값을 넣어 두고 보고에서 알리는 것은 허용하지 않는다
  - **계약은 읽어서 확인한다** — 다른 팩 레포(백엔드 · 공유 패키지)의 코드 · 스키마를 읽는 것은 범위 밖이 아니다(고치는 것만 안 된다)
  - **"추천대로" · "알아서 해"는 선택에만 근거가 된다** — 사용자가 정할 것(표시 형식 · 문구 · 제품 동작)은 그 말로 정하고 계획서에 적은 뒤 진행한다. 사실(필드가 있는지 · 이름 · 단위 · null 여부)은 그 말로 확인되지 않으니 읽어서 확인하고 모르면 멈춘다. 추천안은 확인한 사실 위에서만 세운다("있으면 A, 없으면 B" 대신 먼저 확인)
  - **평범한 구현 선택은 추측이 아니다** — 기존 패턴 · 코딩 규칙 · 승인된 요구에서 나오는 선택(내부 이름 · 스타일 세부값 · 요청된 문구의 표현 · 테스트용 가짜 데이터)은 근거를 밝히고 묻지 않고 정한다. 다만 테스트 값으로 실제 외부 계약을 짐작하거나 제품 정책 · 기본 동작을 새로 정하지 않는다
  - 버그 원인을 좁히는 가설 · 재현 실험은 조사다(시작에 확신은 필요 없다) — 고치는 것은 확인된 원인으로. 승인된 범위를 묻지 않고 끝까지 하는 것은 근거가 있는 일에만 해당한다
- 같은 요구를 더 적은 변경으로 충족하는 방법이 있으면 비용 · 제약과 함께 제안한다(승인된 동작 · 범위를 임의로 바꾸지 않는다). 요청 범위 밖의 정리 · 의존성 업그레이드 · 파일 이동 · 전역 포맷팅 금지 · 포맷은 **작업한 파일만**(설정은 레포 `rules.md`)
- 생성물(`__generated__/` · Relay 아티팩트)은 직접 편집하지 않고 생성 명령으로 만든다
- **무거운 명령은 `<athena>/scripts/heavy.sh` 를 앞에 붙여 한 대에 하나씩** — `pnpm/npm install` · `next build` · `next dev` · `tsc` · 테스트 · `relay` · `pkg:link/unlink` · `docker build`. 137 로 끝나면 폭주한 것이니 원인을 찾기 전에는 다시 돌리지 않고 알린다. 검증 스크립트 · `commit.sh` 는 스스로 줄을 선다. 기다리는 동안 코드 작업을 먼저 하고 `next dev` 는 확인이 끝나면 바로 끈다(잠금 · 감시 기준은 `verify.md` "무거운 명령")
- **멈춘 명령은 TaskStop 이나 확인한 pid 의 `kill <pid>` 로만 끈다** — `pkill` · `killall` · 이름으로 찾아 죽이기 금지(macOS pkill 은 패턴 뒤 옵션을 패턴으로 읽고 `-f` 는 `/Applications` 경로까지 맞춘다). 모든 세션에 `scripts/hooks/process-guard.py` 가 걸린다(`verify.md` "무거운 명령")
- **커밋은 사용자가 요청할 때만 `scripts/commit.sh` 로만** — 지정 파일만 · 워크트리 · 보호 브랜치 제외 · 엄격 검증 · 계획서 `## Commits` 기록. `git commit` 직접 · `add -A` · merge · stash 같은 쓰기는 보호 훅이 막는다 — 꼭 필요하면 아테나 pane 에 이유와 함께 직접 요청한다(거부 이유 · 막는 목록 `git.md`). 커밋 메시지는 레포 최근 관례 · 언어 설정(기본 한국어) · 티켓이 있으면 `feat: PROJ-1234 설명`
- **push · PR 은 사용자가 "PR 올려줘" 라고 할 때만 `scripts/ship.sh` 로만**(레포 하나짜리 작업만 · 여러 레포는 아테나가 순서를 정해 올린다 — `ship.sh` 가 거부하면 아테나 pane 에 직접 요청). **한 마디로 끝까지**: 커밋 안 된 작업은 `commit.sh` 로 먼저 → 미리보기 초안 → 작업 내용으로 제목(`type(범위): 티켓 요약`) · 본문(`git.md` "PR 제목·본문") 정리 → **묻지 않고** `prBase` 로 draft PR. 리뷰 승인 전이면 그대로 올리고 본문 "확인 필요" · 보고에 적는다(main 직접 레포의 push 만 확인받는다)
  - **끝나면 저절로 PR**(`"autoMerge": true` 레포의 레포 하나짜리 작업만): 요청을 끝내고 검증이 통과하면 "PR 올려줘" 없이 같은 흐름을 묻지 않고 돈다 — 열린 PR 이 있으면 push 만 · 조사만 했거나 바뀐 게 없거나 검증이 실패하면 올리지 않는다(지시문은 그 레포일 때만 이 문장을 싣는다)
  - **PR 자동 리뷰 예외**(같은 레포): `[자동 리뷰 → <나>]` 로 온 수정 지시는 묻지 않고 고쳐 `commit.sh` → `ship.sh --auto-push`(그 PR 브랜치에 빨리 감기만). 머지는 에이전트가 하지 않는다 — Claude · Codex 둘 다 승인 + 같은 HEAD 검증 + 충돌 없음 + 사람의 [머지](레포가 `"autoMergeConfirm": false` 면 바로) 뒤 자동 흐름이 squash 로(`docs/pr-auto.md`). 사람 세션의 보호 훅은 그대로
- **토큰 · 키 · 비밀번호는 무조건 노출 금지**(`.env*` · 토큰 · 키 파일 내용은 출력 · 커밋하지 않는다). 값은 어떤 경로로든 출력하지 않는다 — 파일 읽기(`.npmrc` · `.env*` · 키 파일, `git show/diff/log` 포함), `npm/pnpm/yarn config get·list`, `printenv` · `env`, 프로세스 전체 인자(`pgrep -fl` · `ps aux` · `ps -ef` — 환경 변수가 섞인다, `ps -axo pid=,comm=` 만), `echo $…TOKEN`, `gh auth token`, 로그 · 보고 · 커밋 메시지 · 계획서 모두. 확인은 **있는지 · 참조 형태(`${…}`) · 길이 · HTTP 상태 코드만**(`curl -s -o /dev/null -w '%{http_code}'`), 봐야 하면 `sed 's/_authToken=.*/_authToken=***/'` 로 가린 뒤. 실수로 노출되면 즉시 멈추고 알려 폐기 · 재발급을 권한다. 모든 세션에 `scripts/hooks/secret-guard.py` 가 걸려 흔한 경로를 막는다(보안 경계는 아니다 — 규칙이 우선)
- **아테나 스크립트에서 화면(pane · 탭 · workspace)은 `scripts/screen` 으로만** — 데몬 CLI 를 직접 부르지 않는다(pane 결과 읽기도 `scripts/screen pane read <id>` · 자세히 `docs/extending.md` "화면 계층")

## 6. 보고
사용자가 먼저 알고 싶은 것부터, 쉬운 말로 짧게(자세히 `docs/knowledge/common/reporting.md`).
1. **무엇이 달라졌나** — 요청 항목별 완료 / 미완료 / 다르게 한 것과 이유
2. **어디서 확인하나** — 화면 주소 · PR · 바뀐 파일(경로)
3. **검증 결과** — 실패는 원문, 실행 못 한 것은 "실행 못 함". 검증 출력 표는 계획서 Validation 에 그대로
4. **남은 일 · 위험** — 사용자가 해야 할 것(맨 위), 확인 못 해 멈춘 것(무엇을 모르는지 · 확인에 필요한 것), 범위 밖 수정 필요, 다른 서비스 영향. 추측으로 처리한 부분은 있으면 안 된다

- 승인된 범위 안의 후속 일(리뷰 지적 반영 · 재검증 · 다른 pane 에 전달 · Status 갱신)은 끝내고 나서 보고한다. 묻는 것은 범위 · 사용자 동작 · 외부 계약 · 데이터가 달라질 때와 커밋 · push · PR 뿐. 다른 pane(아테나 포함)에 넘길 일은 사용자에게 부탁하지 않고 직접 보낸다(`scripts/screen pane send-text <pane> '[<나> → <받는 쪽>] …'` 다음 `pane send-keys <pane> Enter`)
- **리뷰는 넓은 수정에만**(새 기능 · 구조 변경 · 여러 파일에 걸친 로직 변경 · 보안 · 권한 · 데이터 · 외부 계약에 닿는 코드). 정식 계획서(여러 레포 포함)는 넓은 수정을 보고하면 바로 띄우고(자동 리뷰), 경량(`plans/task/`)은 넓은 수정일 때만 보고 끝에 "리뷰할까요?" 한 줄. 리뷰 지적 반영 · 문구 · 문서 · 작은 수정 뒤에는 다시 띄우지도 묻지도 않는다 — "리뷰해줘" 하면 언제든(띄우는 법 `reporting.md`)
- 그 자리에서 고치지 않은 것은 `docs/issues.md` "등록 기준"대로 — **보안 · 버그(high)만 바로** `issues/<YYYYMMDD>-<레포>-<제목>.md`, 나머지는 보고에 "이슈 후보"로 적고 사용자가 "이슈로" 하면 등록(한 작업은 레포당 하나로 묶는다)
- **📚 배운 것** — 작업을 끝낼 때(`done`) · 사용자가 바로잡을 때(`correction`) · 같은 오류가 3번 날 때(`repeat-error`) 배운 것을 learn 이슈로 올린다(대부분 0개가 정상). **올리기 전에 `docs/knowledge/common/learning.md` 를 읽는다**(무엇을 · 어떻게 · 파일 형식 · 보고 블록은 8절). 공책 · 스킬은 직접 고치지 않는다 — 공책에는 사용자가 [학습] 탭에서 [넣기] 한 것만, 스킬 후보는 아테나가 만든다
- 언어: 한국어로 소통하고 코드 주석도 한국어(영어는 코드 · 파일명 · 기술 용어만). Athena Studio 에서 고른 언어가 있으면 훅이 메시지마다 `[언어 설정]` 으로 알려 주고 그 언어가 먼저다(답 · 계획서 · 이슈 · 커밋 메시지 · 주석 — 템플릿의 제목 · 항목 이름은 스크립트가 읽으니 그대로). 확인하지 못한 것은 사실처럼 쓰지 않고 "확인 못 함"이라고 밝힌다

## 7. 문서를 최신으로 유지하기
- 레포 문서는 `/sync`(또는 `node scripts/sync-fingerprint.mjs`)가 기준 브랜치로 지문을 만들어 갱신한다 — 사실은 반영하고 판단이 든 문장은 "확인 필요", 끝나면 `--accept`(절차 `.claude/skills/sync/SKILL.md`)
- 이 워크스페이스 자체의 구조 변화(에이전트 · 스킬 추가 등)는 sync 가 잡지 않는다 — `docs/extending.md`
- 외부 가이드라인(공개 CLAUDE.md · 스킬 · 플러그인 등)은 통째로 설치하거나 덧붙이지 않는다 — 중복 · 충돌 · 적용 범위를 검토해 필요한 것만 기존 정본 문서에 한국어로 통합한다
