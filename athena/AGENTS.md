# Athena — 프론트·백엔드 멀티 레포 작업 워크스페이스

여러 프론트엔드 레포를 한 곳에서 작업하기 위한 워크스페이스다. **이 문서는 도구에 무관한 공통 규칙**이고, Claude Code·Codex·그 밖의 에이전트가 모두 여기서 출발한다.

도구별 추가 사항은 각자의 문서에 있다.
- Claude Code → `CLAUDE.md` (서브에이전트 위임, 슬래시 커맨드, Plan-First 흐름)
- Codex 등 그 외 → 이 문서 하나로 충분하다. 위임 기능이 없으면 아테나 역할 없이 **직접** 작업하되 아래 규칙과 지식을 그대로 따른다

## 0. 첫 실행 — 팩이 없으면 이것부터

`athena.config.json` 이 없거나, 거기에 `pack` 이 없거나, 팩의 `pack.json` 에 `repos` 가 비었으면 **아직 회사가 등록되지 않은 아테나**다. 사용자의 첫 메시지가 무엇이든 먼저 한 줄로 알리고 **`docs/setup.md`** 절차(레포 찾기 → 팩 → 에이전트·지식 → 서비스 문서 → QA 초안 → 검증 → 지문 → 다이어그램)를 돈다. Athena Studio pane 에서 켜면 세션 시작 훅(Claude `.claude/settings.json` · Codex `.codex/hooks.json`)이 화면을 세팅한 뒤 첫 실행 지시를 pane 에 대신 입력한다(Claude `/setup` 이 같은 문서를 따른다).
환경 변수 `ATHENA_AGENT` 가 있는 창(바깥 도구가 띄운 관리 창)에서는 하지 않는다.
Jev 키(선택 · 사람마다 본인 키)는 첫 실행 7-2단계가 묻고, 나중에 "Jev 키 등록해줘" 라고 해도 같은 절차다 — 키는 대화로 받지 않고 사용자가 입력 창(`node scripts/jev-key.mjs`)에 직접 넣는다.

## 1. 담당 레포와 기준 브랜치

**담당 레포·에이전트·라우팅은 팩에 있다 — `pack/ROUTING.md` 를 먼저 읽는다**(Claude Code 는 `CLAUDE.md` 가 자동으로 불러온다). 기계 정본은 팩의 `pack.json`(코어 `athena.config.json` 의 `pack` 이 가리키는 폴더). 경로는 어디서나 `repos/<레포>`이며 `scripts/setup.sh`가 심볼릭 링크를 만든다. 팩 파일은 `athena pack link` 가 코어의 정해진 자리(`.claude/agents`·`docs/knowledge/<레포>`·`scripts/verify/<레포>.sh` …)에 링크로 건다.

**여러 팩 구조**(본체에 활성 링크 `.pack-data` 가 있다)면 **팩마다 본체가 따로**다 — 주 본체 `~/.athena-studio/core`(main 브랜치 · 앱 번들에서 온 설치본 — 코어 정비는 본체가 아니라 코어 정본 레포에서 브랜치 · PR 로, `CLAUDE.md` 갈래 표)와 팩 본체 `~/.athena-studio/bodies/<id>`(같은 git 저장소의 워크트리 · 브랜치 없이 배포 커밋)가 각자 팩 하나에 고정되어 동시에 켜진다. 본체 안의 `pack`·`plans`·`issues`·`repos`·`.worktrees`·`archive` 는 **그 본체 팩**의 데이터(`~/.athena-studio/data/packs/<id>/…`)를 가리키는 링크다. 계획서·이슈는 언제나 본체 기준 논리 경로(`plans/…md`)로 다루고 실제 경로로 풀지 않는다. 아테나 세션은 본체에서만, 데이터 폴더에서는 세션을 켜지 않는다. 다른 팩은 `bin/athena pack open <id>` 로 그 본체를 열고(없으면 만든다) 그 폴더에서 켠다 · 코어 업데이트는 앱이 켜질 때 `bin/athena update --from <번들>`(앱이 들고 온 코어 · 모든 본체 한 번에 · 일하는 본체는 건너뜀) · 가져오기는 `bin/athena pack …`(`docs/pack.md` "여러 팩").

**기준 브랜치 = 운영 반영분.** 문서와 지식 베이스는 이 브랜치(`pack.json` 의 `branch`)를 읽어 만든 것이다. 로컬 작업 트리가 그보다 뒤처져 있으면 문서와 코드가 다를 수 있는데, **그건 문서 오류가 아니다.** 작업 전 `git status --short --branch`로 얼마나 벌어졌는지 확인하고 보고에 적는다.

**범위 밖**: 팩 표에 없는 레포. 변경이 필요하면 작업을 멈추고 사용자에게 알린다. 작업 브랜치 base 는 `pack.json` 의 `prBase`.

### 어느 레포인지 고르기
- 팩 `ROUTING.md` "어느 레포인지 고르기" 를 따른다. 해석이 둘 이상이면(같은 이름의 화면이 여러 레포에 있는 등) **반드시 사용자에게 확인**한다
- **프론트와 백엔드가 함께 바뀌면 백엔드 먼저** — 공유 패키지 먼저와 같은 규칙. 계획서 공통 스펙에 엔드포인트·요청·응답 형식을 적고, 백엔드 에이전트가 보고한 "계약 변경"을 프론트 에이전트에 넘긴다

## 2. 무엇을 읽고 시작할 것인가

### 2.1 규칙은 세 층 — 충돌하면 뒤가 우선

| 층 | 위치 | 내용 |
|---|---|---|
| 1. 팀 공통 | `docs/knowledge/common/` | `coding.md`(코드) · `git.md`(Git) · `reporting.md`(보고) · `verify.md`(검증) |
| 2. 레포 규칙 | `docs/knowledge/<레포>/rules.md` | 그 레포에서 **공통과 다른 점**과 고유 규칙 |
| 3. 레포 원문 | 각 레포 안 | 레포의 `CLAUDE.md`·`.ai/*.md`·`README.md` 등 |

레포 원문이 코드와 다르면 **코드를 우선**하고 차이를 보고한다.

### 2.2 항상 읽는 것 (작업 종류와 무관)

**knowledge 전체를 선행 로딩하지 않는다.** 대신 아래는 작업이 아무리 작아도 예외 없이 적용된다.

- 5절 **작업 규칙** — 담당 범위, 커밋은 요청 시 `commit.sh`·push/PR 은 요청 시 `ship.sh`(레포 하나짜리), 시크릿 취급, 생성물 편집 금지
- 대상 레포 `docs/knowledge/<레포>/rules.md`의 **"필수" 절** — 용어 규칙, 금지 사항, 허용 범위 예외
- 대상 레포 `docs/knowledge/<레포>/gotchas.md` **전체** — 함정은 어느 작업에서 밟을지 미리 알 수 없다. 문구 한 줄을 고치다가 날짜 변환·인증·생성물 함정에 걸리는 일을 막기 위해 크기와 무관하게 읽는다. 공책이 나뉘어 `gotchas/<폴더>.md`(화면 파일)가 있으면 **작업할 파일이 그 폴더 안일 때 그 화면 파일도 전부** 읽는다(`gotchas.md` 맨 위 화면 목차가 가리킨다 · 기준 `docs/knowledge/common/learning.md` 7절). 작업 중 다른 화면 폴더로 넓어지면 그 화면 파일도 읽는다
- 대상 repo/app/worktree가 무엇인지 확인 (`git status --short --branch`)
- 아테나 **자체** 작업(`repo: athena` — 스크립트·현황판·규칙 문서)이면 `docs/knowledge/athena/gotchas.md`

필수 규칙은 선택 로딩 문서 깊숙이 옮기지 않는다. `rules.md`는 짧은 진입점으로 유지하고 긴 설명·예제는 `structure`/`patterns`로 보낸다.

> **무엇이 자동으로 들어오는지는 도구마다 다르다** (2026-09-17 Claude Code 서브에이전트로 실측):
> - 자동 주입됨 — `CLAUDE.md`, `AGENTS.md`, `.claude/rules/*.md` 4개, 에이전트 프로필 본문
> - **자동 주입되지 않음** — `docs/knowledge/**` 전부. `rules.md`의 "필수" 절과 `gotchas.md`는 **직접 읽어야 한다**
>
> 그래서 팀 공통 코드 규칙(변수명·`any` 금지·성능)은 Claude Code 에서는 `.claude/rules/coding-standards.md` 로 항상 들어오지만, **그렇지 않은 도구(Codex 등)는 `docs/knowledge/common/coding.md` 를 직접 읽어야 한다.** 자동 주입을 전제하지 말고, 필요한 규칙이 실제로 눈앞에 있는지 확인한다.

### 2.3 그다음은 작업 유형에 따라 필요한 절만 읽는다

| 작업 유형 | 추가로 읽을 것 |
|---|---|
| 문구·스타일 국소 수정 | 대상 파일과 인접 사용처. `patterns`·`workflows`·`structure`는 불필요 (`gotchas`는 2.2에서 이미 읽었다) |
| 새 화면·기능 | 해당 `workflows.md` 절 → `patterns.md`가 가리키는 **실제 파일** → `structure.md`의 라우트·권한 표 |
| API·폼·상태 변경 | 해당 API/폼 pattern, 타입·생성 설정, `rules.md` API 절 |
| 버그 수정 | 재현 근거, 관련 코드·테스트. 과거 이유가 필요할 때만 History |
| 구조 변경·공유 패키지 | `structure.md`와 소비처, 해당 workflow, 담당 범위·영향 규칙 |
| 기존 작업 재개 | 해당 plan의 **Checkpoint**, 현재 diff·worktree, 다음 단계에 필요한 코드 |

- **새 구현에서 workflow와 대표 코드 확인을 생략하지 않는다.** 국소 수정에만 면제된다
- 작업 도중 범위가 커지면(문구 수정 → 새 화면) **로딩 분류도 다시 한다**
- 문서 목차·제목·키워드 검색으로 필요한 절을 찾는다. 파일 분할은 실제로 찾기 불편할 때만
- 자동 주입된 내용과 직접 읽은 내용을 구분하고, 같은 세션에서 바뀌지 않은 문서를 이유 없이 다시 읽지 않는다
- 링크를 적어두는 것은 읽은 것이 아니다. 규칙은 실제로 적용 가능한지 확인해야 한다

### 2.4 무엇을 믿을 것인가 — 지시 / 사실 / 상태 / 기록

"코드가 우선"은 **현재 구현을 판단하는** 원칙이다. 코드가 요구사항이나 권한·보안 규칙을 무효화한다는 뜻이 아니다.

| 종류 | 무엇이 권위인가 |
|---|---|
| **지시** | 실행 환경의 상위 지시, 현재 사용자 요청, 승인된 계획의 범위. 요청이 계획을 바꾸면 plan에 반영한다 |
| **현재 구현 사실** | 대상 repo/app/worktree의 코드·설정과 검증 결과. 그다음이 레포 원문, 그다음이 출처·기준 커밋이 적힌 knowledge |
| **진행 상태·의도** | 해당 plan. "완료" 기재만으로 확정하지 않고 diff와 검증 근거를 본다 |
| **Memory·History** | 현재 사실의 근거가 **아니다.** 어디를 볼지, 과거에 왜 그랬는지 찾는 단서로만 쓴다 |
| **Skill·대화 요약** | 절차 안내 또는 작업 기록. 그 안의 기술 사실도 필요하면 현재 코드로 검증한다 |

**위 어디에서도 확인되지 않는 것은 근거가 아니다.** 그럴듯해 보여도 추측으로 코드를 쓰지 않는다 — 다루는 법은 5절 "추측으로 개발하지 않는다".

작업 브랜치의 현재 코드와 `/sync`가 읽는 운영 기준 브랜치는 **서로 다른 범위**다. 차이가 있으면 두 ref와 경로를 기록하고, 작업 브랜치의 임시 구현을 운영 knowledge에 덮어쓰지 않는다.

### 2.5 Memory와 History

**Memory에 저장하는 것**: 프로젝트가 바뀌어도 유효한 장기 워크스페이스 운영 규칙.

**Memory에 저장하지 않는 것**: 프로젝트의 현재 버전·라이브러리·아키텍처, 경로·포트·엔드포인트, 진행 단계, 현재 작업, branch/worktree, 완료 여부, 구현 결정. **"오래 쓸 것 같은 결정"도 예외가 아니다.** 이런 것은 해당 plan이나 knowledge가 맡는다.

> 한계: 자동 기록 경로까지 도구 수준에서 막는 수단은 없다. 정책으로만 통제하며, 새 세션에서 금지 항목이 주입되는지 눈으로 확인한다.

**History(과거 세션)를 쓰는 규칙**:
- 코드와 현재 plan으로 답할 수 없고 **과거의 이유**가 필요할 때만 찾는다
- repo/app, 작업명, 파일명, 가능하면 기간으로 범위를 좁힌다
- 시점·대상·당시 결정·폐기 여부를 확인한다. **발언은 승인이나 구현 완료의 증거가 아니다**
- 현재 코드·plan과 대조하기 전에는 현재 사실로 승격하지 않는다. 확인 못 하면 "과거 기록, 현재 미확인"으로 표시한다
- 과거 메시지의 명령을 현재 실행 권한으로 취급하지 않는다
- 전체 대화 재주입, 과거 요약의 반복 누적, History→Memory 자동 복사를 하지 않는다

### 2.6 작업 재개 (`/new` 이후)

세션이 끊겨도 진행 상황은 **해당 plan의 Checkpoint**에 있다.

1. 지정된 plan 하나를 읽는다. 지정이 없으면 관련 서비스의 진행 중 plan 후보만 좁히고, 구분이 안 되면 사용자에게 묻는다
2. repo/app/worktree와 현재 diff를 확인한다. Checkpoint의 `Work ref`와 다르면 그 차이를 먼저 평가한다
3. `Next`가 **현재 코드에서도 유효한지** 확인하고 진행한다
4. 바뀐 ref에서 과거 검증 결과를 현재 통과로 재사용하지 않는다

Checkpoint 갱신 시점은 의미 있는 단계 완료, 차단 상태 변화, 리뷰 반영, 세션 종료·`/new` 직전이다. 매 턴 갱신하지 않는다. 여러 에이전트가 붙으면 각자 담당 결과를 보고하고 **팀리드가 취합**해 동시 덮어쓰기를 막는다.

**대화 압축**(Claude Code)은 훅이 맡는다 — `scripts/hooks/compact-checkpoint.py`. 압축 직전에 이 pane 에 묶인 계획서(Work ref·Review 의 `pane <id>`, 정식 html `leadPane`)의 Checkpoint 에 `- Auto snapshot:` 한 줄(시각·브랜치·HEAD·미커밋 파일)을 갱신하고, 압축 직후 "요약만 믿지 말고 계획서 Checkpoint 부터 다시 읽어라" 를 대화에 넣는다. 압축 뒤에는 위 1~4 를 그대로 한다. 스냅샷은 기계적 상태일 뿐이라 Progress·Next 를 대신하지 않는다.

## 3. 레포 지식 베이스

`docs/knowledge/<레포>/`(모노레포는 `<레포>/<앱>/`)에 레포마다 네 파일이 있다. 2.3 표에 따라 **필요한 절만** 읽는다.

| 파일 | 쓰임 |
|---|---|
| `structure.md` | 디렉토리·라우트·스크립트 맵 |
| `patterns.md` | **"이런 걸 만들 땐 이 파일을 보고 따라라"** 대표 예시 경로 |
| `workflows.md` | 새 화면 추가 등 반복 작업 절차 체크리스트 |
| `gotchas.md` | 함정·이력·문서와 코드의 불일치 |

레포마다 관례가 다르므로 다른 레포의 패턴을 가져오면 안 된다. 설치만 되어 있고 쓰이지 않는 라이브러리는 `gotchas.md`에 적혀 있다.

`.claude/agents/<이름>.md`는 **역할·담당 범위·지식 진입점**이다. 기술 사실의 정본이 아니다 — 버전·구조·명령은 knowledge와 실제 코드에서 확인한다. frontmatter는 Claude Code 전용이지만 본문은 도구와 무관하게 유효하다.

## 4. 검증

에이전트와 리뷰어가 **같은 스크립트**를 기준으로 하고, 그 출력 표를 보고서에 그대로 붙인다.

```bash
scripts/verify/<레포>.sh [<앱|패키지…>]          # 에이전트 — 레포마다 하나, 목록·인자는 pack/ROUTING.md "검증 스크립트"
scripts/verify/reuse.sh <레포> [<앱|패키지…>]    # 리뷰어·commit.sh — 같은 트리로 이미 통과했으면 다시 돌리지 않는다
```

**같은 내용을 여러 번 돌리지 않는다.** 검증 스크립트가 통과하면 "트리 내용 + 검증 스크립트 + 인자" 열쇠로 레포 밖에 기록하고, `reuse.sh` 는 같은 열쇠면 그 표를 `♻️ 재사용(@시각)` 으로 다시 찍는다 — 한 글자라도 다르면 다시 돈다(`docs/knowledge/common/verify.md` "재사용"). 오래 걸리는 단계는 관련 파일이 바뀐 때만 돌기도 한다(예: 화면 회귀는 화면 파일이 바뀐 때만 — `scripts/verify/changed-screen.sh`, 표에 `⏭ 건너뜀(규칙)`).

실행 전 확인할 것과 결과 해석은 `docs/knowledge/common/verify.md`에 있다. 요약하면 Node 버전을 레포 `.nvmrc`에 맞추고(`nvm use`), 생성물(Orval·Relay)이 없으면 타입 검사가 건너뛰어진다는 점이다. 워크트리를 검증할 때는 `ATHENA_VERIFY_DIR=<워크트리>`를 붙인다(없으면 메인 체크아웃을 검증한다). **실행하지 못한 검증을 통과한 것처럼 보고하지 않는다.**

## 5. 작업 규칙 (2.2의 **필수 규칙** — 작업 종류와 무관하게 항상 적용)

- **바꾸는 작업은 모두 계획서 하나에 묶인다.** 사용자가 정할 것이 있거나 여러 레포·담당을 맞춰야 하면 정식 계획서(`docs/plan-template.md` md + 같은 이름 html 결정 콘솔 — 사용자가 콘솔에서 고르고 [이대로 진행] 을 누르면 아테나에 전달, 확정값은 md·html 에 기록), 아니면 경량 계획서(`plans/task/…md`, `docs/plan-template-light.md` — `node scripts/new-plan.mjs` 가 만든다). 코드·설정·문서를 바꾸면서 계획서 없이 하는 예외는 없다. 같은 작업의 추가 요청은 그 계획서에 이어 쌓고, 아무것도 바꾸지 않는 질문·설명에는 만들지 않는다. 정식 대상이어도 사용자가 "바로 고쳐"라고 명시하면 경량으로 바로 진행하되, 보고에 그 사실을 적는다. **경량인지 정식인지는 시작할 때 한 줄로 알린다**(`📋 경량으로 진행합니다 — 이유 · 경로`). 끝나면 계획서 Checkpoint(Status·Progress·Validation)를 채운다
- **작업은 새 작업 브랜치에서 시작한다.** 지금 체크아웃된 브랜치에 그냥 얹지 않는다. 브랜치를 딸 기준은 팩 `pack.json` 의 `prBase`(개발 브랜치)이고, 문서·지식의 기준(`branch`, 운영 반영분)과 다르다. 기본은 **워크트리**로 만들어 메인 체크아웃을 건드리지 않는다 — 레포에 미커밋 변경이 있어도 시작할 수 있고 여러 작업을 동시에 돌릴 수 있다. 미커밋 변경을 stash 하지 않는다(남의 작업일 수 있다). 절차는 `docs/knowledge/common/git.md` "작업 브랜치 만들기". **예외 — main 직접 레포**(팩 레포에 `"direct": true`): 브랜치·워크트리·PR 없이 메인 체크아웃의 작업 브랜치(`prBase`)에서 바로 작업하고, "커밋해줘" 는 `commit.sh`, "올려줘" 는 `ship.sh`(PR 대신 빨리 감기 push). 시작 전에 메인 체크아웃이 그 브랜치이고 최신인지 확인한다(`docs/pack.md`)
- 담당 범위 밖은 수정하지 않는다. 필요하면 멈추고 보고한다
- 작업 중 요청이 여러 레포·API·구조 변경으로 커지면 멈추고 알린다 — 정식 계획서로 옮긴다(아테나가 맡는다)
- **버그 수정**은 계획서에 재현 조건·기대 동작·실제 동작을 먼저 적는다. 재현하지 못했으면 확보한 로그·코드 근거와 미확인 부분을 나눠 적고 원인을 확정하지 않는다. 고치기 전에 재현 테스트 또는 재현 절차로 실패부터 확인하고(자동 테스트를 강제하지는 않는다), 고친 뒤 같은 방법으로 다시 확인해 전·후 결과를 남긴다. 재현 미확인·실행 불가를 통과로 보고하지 않는다. 원인이 프론트 밖(API 응답·공유 패키지)이면 알린다
- 요청에 해석이 여러 개면 기존 코드·설정·승인된 결정으로 먼저 좁힌다. 범위·사용자 동작·데이터·권한·외부 계약이 달라지는 해석이 남으면 선택지·영향·추천안을 제시하고 확인받는다(그 결정에 기대지 않는 조사·작업은 계속하되, 아테나의 디스패치는 확정 뒤에 한다). 규칙으로 정해지는 사소한 구현 선택은 근거를 밝히고 진행한다
- **추측으로 개발하지 않는다.** 코드만 보고는 알 수 없는 사실 — 외부 계약(API 응답 모양·필드·키 이름·에러 코드), 제품 정책·기본 동작, 데이터의 뜻 — 은 근거(2.4 — 지금 코드·실행·검증 결과, 출처를 확인한 레포 원문·문서, 사용자 말, 승인된 계획서)가 있을 때만 코드에 넣는다. 없으면 먼저 코드를 찾아 읽고·돌려 보고·문서를 확인한다. 그래도 확인할 수 없으면 그 부분만 멈추고(그 판단에 기대지 않는 작업은 계속한다) 계획서 Blocked 에 적은 뒤 **모르는 것을 모아 한 번에** 묻는다 — 항목마다 무엇을 모르는지 · 어디까지 확인했는지 · 확인에 필요한 것 · 추천안. 물을 때 같은 내용으로 **요청을 연다**(`bin/athena request open --kind question …` — 현황판 · 스튜디오 앱의 "확인 필요" 는 이것만 센다) · 대화로 답을 받으면 `request answer <id> --by chat`, 답이 `[요청 <id>]` 를 달고 pane 으로 오면 받자마자 `request ack <id>`(`docs/requests.md`). 더 할 일이 없으면 Status 를 `blocked` 로 바꾼다(현황판·메뉴 막대에 막힘으로 떠서 pane 을 안 보고 있어도 안다). 그럴듯한 임시값을 넣어 두고 보고에서 알리는 것은 허용하지 않는다
  - **계약은 읽어서 확인한다** — 다른 팩 레포(백엔드·공유 패키지)의 코드·스키마를 읽는 것은 담당 범위 밖이 아니다(고치는 것만 안 된다). "내 담당이 아니라 안 봤다"로 넘기지 않는다
  - **"추천대로"·"알아서 해"는 선택에만 근거가 된다** — 사용자가 정할 것(표시 형식·문구·제품 동작)은 그 말로 정하고 계획서(결정·Progress)에 적은 뒤 진행한다. 사실(그 필드가 있는지·이름·단위·null 여부)은 그 말로 확인되지 않는다 — 읽어서 확인하고, 없거나 모르면 그대로 멈춘다. 그래서 추천안은 확인 안 된 사실을 전제로 세우지 않는다("있으면 A, 없으면 B" 대신 먼저 확인하고, 확인한 사실 위에서 추천한다)
  - **평범한 구현 선택은 추측이 아니다** — 기존 패턴·코딩 규칙·승인된 요구에서 나오는 선택(내부 변수·함수 이름, 스타일 세부값, 요청된 문구의 표현, 테스트용 가짜 데이터)은 재량으로 정하고 묻지 않는다(바로 위 "사소한 구현 선택"). 다만 테스트 값으로 실제 외부 계약을 짐작하거나 제품 정책·기본 동작을 새로 정하지는 않는다
  - 버그 원인을 좁히는 가설·재현 실험은 조사다 — 실험을 시작하는 데 확신이 필요하지는 않고, 고치는 것은 확인된 원인으로 한다
  - 승인된 범위 안을 묻지 않고 끝까지 하는 것은 근거가 있는 일에만 해당한다
- 같은 요구를 더 적은 변경으로 충족하는 방법이 있으면 비용·제약과 함께 제안한다. 승인된 동작·범위를 임의로 바꾸지는 않는다
- 요청 범위 밖의 정리·의존성 업그레이드·파일 이동·전역 포맷팅 금지
- 포맷은 **작업한 파일만**. 설정은 레포마다 다르다(`<레포>/rules.md`)
- 생성물(`__generated__/`, Relay 아티팩트)은 직접 편집하지 않고 생성 명령으로 만든다
- **무거운 명령은 한 번에 하나씩, 컴퓨터가 버틸 때만** — `pnpm/npm install`·`next build`·`next dev`·`tsc`·테스트·`relay`·`pkg:link/unlink`·`docker build` 는 앞에 `<athena>/scripts/heavy.sh` 를 붙여 돌린다(한 대 공용 잠금 + 1분 부하가 코어×1.2 를 넘으면 내려갈 때까지 대기, 끝나거나 실패해도 잠금을 푼다). **도는 동안 감시해서** 자식 프로세스가 300개를 넘거나 메모리 여유가 15% 아래면 그 명령과 자식을 모두 끄고 137 로 끝낸다 — 그러면 폭주한 것이니 원인을 찾기 전에는 다시 돌리지 않고 알린다. 검증 스크립트(`scripts/verify/*.sh`)·`commit.sh` 검증은 스스로 줄을 선다. 기다리는 동안은 코드 작업을 먼저 하고, `next dev` 는 확인이 끝나면 바로 끈다(잠금을 쥐고 있다). 여러 에이전트를 동시에 띄워도 무거운 명령은 이걸로 자동 조절된다(2026-10-02 동시 빌드로 컴퓨터가 죽은 뒤)
- **커밋은 사용자가 요청할 때만, `scripts/commit.sh` 로만 한다** — 지정 파일만·워크트리·보호 브랜치 제외·엄격 검증·계획서 `## Commits` 기록(`docs/knowledge/common/git.md`). **push·PR 도 사용자가 "PR 올려줘" 라고 할 때만, `scripts/ship.sh` 로만 한다** — 레포 하나짜리 작업만. **"PR 올려줘" 한 마디로 끝까지 간다**: 커밋 안 된 작업이 있으면 `commit.sh` 로 먼저 커밋하고, 작업 내용으로 제목·본문(공통 형식 `git.md` "PR 제목·본문")을 정리해 **묻지 않고** `prBase` 로 draft PR. 리뷰 승인 전이면 그대로 올리고 본문 "확인 필요"·보고에 적는다(main 직접 레포의 push 만 지금처럼 확인받는다). 여러 레포에 걸친 작업은 아테나가 순서를 정해 올린다
  - **끝나면 저절로 PR**(`"autoMerge": true` 레포의 레포 하나짜리 작업만 · 2026-10-25 결정): 에이전트가 요청을 끝내고 검증 스크립트가 통과하면 사용자 "PR 올려줘" 없이 같은 흐름(`commit.sh` → `ship.sh` 미리보기 → 제목 · 본문 정리 → draft PR)을 묻지 않고 돈다 — 이미 열린 PR 이 있으면 그 브랜치에 push 만. 조사만 했거나 바뀐 게 없으면 올리지 않고, 검증이 실패하면 올리지 않고 보고한다. 위임 지시문은 그 레포일 때만 이 문장을 싣는다(`delegate.sh`)
  - **예외 하나 더 — PR 자동 리뷰**(팩 레포 `"autoMerge": true` 인 레포의 레포 하나짜리 PR 만 · 기본 꺼짐 · `docs/pr-auto.md`): `[자동 리뷰 → <에이전트>]` 로 온 수정 지시는 묻지 않고 고쳐 `commit.sh` 로 커밋하고 `ship.sh --auto-push`(이미 열린 그 PR 브랜치에 빨리 감기만)로 올린다. 머지는 Claude · Codex 둘 다 승인 + 같은 HEAD 검증 통과 + 충돌 없음 + 사람이 머지 확인 요청에서 [머지] 를 고를 때만(레포가 `"autoMergeConfirm": false` 면 묻지 않고 바로) 자동 흐름이 squash 로 한다. 사람 세션의 보호 훅은 그대로다
- `.env*`, 토큰, 키 파일 내용은 출력·커밋하지 않는다. **토큰·키·비밀번호는 무조건 노출 금지.** 값은 어떤 경로로든 출력하지 않는다 — 파일 읽기(`.npmrc`·`.env*`·키 파일, `git show/diff/log` 포함), `npm/pnpm/yarn config get·list`, `printenv`·`env`, 프로세스 전체 인자(`pgrep -fl`·`ps aux`·`ps -ef` — 환경 변수가 섞여 나온다, `ps -axo pid=,comm=` 만), `echo $…TOKEN`, `gh auth token`, 로그·보고·커밋 메시지·계획서 모두. 확인이 필요하면 **있는지·참조 형태(`${…}`)·길이·HTTP 상태 코드만** 본다(`curl -s -o /dev/null -w '%{http_code}'`). 봐야 하면 `sed 's/_authToken=.*/_authToken=***/'` 로 가린 뒤. 실수로 노출되면 즉시 멈추고 사용자에게 알려 폐기·재발급을 권한다. 모든 세션(아테나·FE·reviewer)에 `scripts/hooks/secret-guard.py` 가 걸려 흔한 경로를 막는다(보안 경계는 아니다 — 규칙이 우선)
- **아테나 스크립트에서 화면(pane·탭·workspace)은 `scripts/screen` 으로만 다룬다** — Athena Studio 데몬 CLI 를 직접 부르지 않는다(화면 계층만 고치면 스크립트가 그대로 돌게). 에이전트 pane 결과 읽기도 `scripts/screen pane read <id>`. 동작·백엔드·지킴이(`scripts/screen-lint.sh`)는 `docs/extending.md` "화면 계층"

## 6. 보고 형식

사용자가 먼저 알고 싶은 것부터, 쉬운 말로 짧게.

1. **무엇이 달라졌나** — 요청 항목별 완료 / 미완료 / 다르게 한 것과 이유
2. **어디서 확인하나** — 화면 주소·PR·바뀐 파일(경로)
3. **검증 결과** — 실패는 원문, 실행 못 한 것은 "실행 못 함". 검증 스크립트 출력 표는 계획서 Validation 에 그대로 남긴다
4. **남은 일·위험** — 사용자가 해야 할 것(있으면 맨 위), 확인 못 해 멈춘 것(무엇을 모르는지 · 확인에 필요한 것), 범위 밖 수정 필요, 다른 서비스 영향. 추측으로 처리한 부분은 있으면 안 된다(5절)

승인된 범위 안의 후속 일(리뷰 지적 반영·재검증·다른 pane 에 전달·Status 갱신)은 보고로 넘기지 않고 끝내고 나서 보고한다. 묻는 것은 범위·사용자 동작·외부 계약·데이터가 달라질 때와 커밋·push·PR 뿐이다. 다른 pane(아테나 포함)에 넘길 일은 사용자에게 전달을 부탁하지 않고 직접 보낸다(`scripts/screen pane send-text <pane> '[<나> → <받는 쪽>] …'` 다음 `pane send-keys <pane> Enter`).

보고 다음 리뷰 — **리뷰는 넓은 수정에만 한다**(넓은 수정(새 기능 · 구조 변경 · 여러 파일에 걸친 로직 변경 · 보안 · 권한 · 데이터 · 외부 계약에 닿는 코드) · 2026-10-25). **정식 계획서(여러 레포 작업 포함)는 넓은 수정을 보고하면 바로 리뷰를 띄운다**(자동 리뷰). **경량 계획서(`plans/task/`)는 넓은 수정일 때만 보고 끝에 "리뷰할까요?" 한 줄** 붙이고 사용자가 "리뷰해줘" 할 때 띄운다. 리뷰 지적 반영 · 문구 · 문서 · 작은 수정 뒤에는 다시 띄우지도 묻지도 않는다 — "리뷰해줘" 하면 언제든(Claude Code 는 `CLAUDE.md` 4단계 · 띄우는 법 `docs/knowledge/common/reporting.md`).

작업 중 찾았지만 **그 자리에서 고치지 않은 것**은 `docs/issues.md` **"등록 기준"** 을 따른다 — 버그·보안·데이터 위험 / 결정 필요 / 담당이 분명한 할 일만 등록하고, 선택 항목·계획서 Next 에 있는 일·정보성 목록·확인 안 된 추측은 등록하지 않는다. 한 작업에서 나온 것은 레포당 하나로 묶고(열린 이슈가 있으면 덧붙이기), **보안·버그(high)만 바로 등록**, 나머지는 보고에 "이슈 후보"로 적고 사용자가 "이슈로" 하면 등록한다. 파일은 `issues/<YYYYMMDD>-<레포>-<제목>.md`, 형식은 `docs/issues.md`. 아테나 현황판(`scripts/board/server.mjs`, Claude Code 는 `/board`)의 이슈 칸에 뜬다.

**📚 배운 것 (학습 루프)** — 에이전트는 아래 **세 가지 순간**에 배운 것을 학습 후보(learn 이슈)로 올린다(`signal:`). 공책에는 사용자가 현황판 [학습] 탭에서 [넣기]를 고른 것만 들어간다.
- `done` **작업을 끝낼 때** — 보고 끝에 0~3줄. 끝낼 때는 **PR 을 올리고 보고할 때**(`ship.sh` — "PR 올려줘" 한 마디의 끝), 여러 레포 작업(PR 은 아테나가 올린다)이면 아테나에 넘기는 마지막 결과 보고, PR 없이 끝나는 작업(조사·확인)은 마지막 결과를 보고할 때다. 요청마다 붙이지 않는다
- `correction` **사용자가 바로잡을 때**("그거 아니야", "이렇게 해") — 가장 중요한 신호다. 그 레포·작업 방식에 대한 교정이면 그 자리에서 이슈를 만들고 한 줄로 알린다. 그 요청에만 해당하는 지시면 만들지 않는다
- `repeat-error` **같은 오류가 3번 날 때**(코드 규칙 "오류 대응") — 원인이 레포 고유 함정이면
- `review` **배우기 검토자** — **내 작업의 PR 이 모두 머지되면**(어느 브랜치로든 · 현황판이 5분마다 감지) 그 작업의 계획서(요청·결정·결과) · 대화 기록(줄여서 · 도구 결과 본문 빼고 · 비밀값 가림) · 머지된 PR 의 바뀐 코드 · 리뷰 댓글을 별도 Claude 가 읽고 빠진 것을 learn 이슈로 보탠다(`scripts/learn-review.mjs` — 역할은 `.claude/agents/learn-reviewer.md`, 뒤에서 도는 검토 하나가 차례로). 머지되지 않은 시도는 배우지 않는다. 에이전트가 이미 올린 것과 겹치면 덧붙이거나 건너뛴다 — 에이전트는 위 세 순간에 그대로 올린다

무엇을 학습하고 어떻게 적나 — **정본 `docs/knowledge/common/learning.md`**(넣을 것 · 버릴 것 · 쉬운 말로 쓰는 법 · 중복이면 기존 줄 강화 · 스킬 후보). 학습 후보를 올리기 전에 읽는다. 요약: 다음 평범한 작업에서 다시 마주치고 모르면 실제로 잘못되는 것만, 대부분 0개가 정상, 이미 코드로 고친 버그·한 번 있었던 일·FE 밖 원인은 빼고, 대화 문장을 옮기지 말고 그 작업을 모르는 사람도 알게 쓴다

어디에 담나
- 아테나 자체 작업에서 배운 것은 `target: docs/knowledge/athena/gotchas.md#절`
- 아테나 루트의 `issues/<YYYYMMDD>-<영역>-learn-<이름>.md`(워크트리 pane 이면 아테나 루트 절대 경로로) — `repo: athena` · `kind: knowledge` · `signal:` · `basis: code | run`(근거가 사용자 말뿐이면 올리지 않는다 — 취향일 수 있다, learning.md 1-1) · `source: <계획서>` · `target: <docs/knowledge/<영역>/gotchas.md#절 | skill:<이름>>`(공책은 gotchas.md 만) · `scope: <코드 폴더>`(그 화면을 만질 때만 걸리면 — 예 `app/orders`, 레포 어디서든이면 생략) · 기존 줄을 고치는 것이면 `strengthen: <그 줄 그대로>`. 본문은 `## 무엇을 배웠나` · `## 왜 중요한가` · `## 공책에 넣을 문장` · `## 어디서 배웠나`(learning.md 3절)
- 현황판 **[학습] 탭**에 뜬다(아테나·서비스 칸반에는 안 뜬다). 공책 기존 줄과 같은 내용이라고 Jev 가 아주 높게 본 후보는 휴지통으로 저절로 빠진다(Jev 키를 등록한 사람만 · `learning.md` 6절). 사용자가 [넣기]·[고쳐서 넣기]·[버리기] — 넣으면 공책 끝 `## 학습` 절에 한 줄, 쉬운 설명 기록은 `docs/knowledge/learned/` 에 남고 [학습] 탭에서 언제든 수정·삭제
- 공책·스킬은 **직접 고치지 않는다.** 스킬 후보("🛠 스킬로 만들까요?")를 고르면 아테나가 만든다(`docs/extending.md` "학습으로 스킬 만들기")

```
📚 배운 것 (다음 작업용 · 승인 전)
- <쉬운 한 줄 제목> — 왜 중요한가 한 줄 → [학습] 탭 (issues/<…>-learn-<이름>.md)
- [스킬 후보 · 반복 N회] <절차 한 줄> → [학습] 탭
- (없으면) 없음
```

한국어로 소통하고 코드 주석도 한국어로 쓴다 — Athena Studio 에서 고른 언어가 있으면 훅(`scripts/hooks/language.py`)이 메시지마다 `[언어 설정]` 으로 알려 주고, 그 언어가 먼저다(답 · 계획서 · 이슈 · 커밋 메시지 · 주석 · 템플릿 제목 · 항목 이름은 그대로). 확인하지 못한 것은 사실처럼 쓰지 않고 "확인 못 함"이라고 밝힌다 — 추측으로 구현하지는 않는다(5절).

## 7. 문서를 최신으로 유지하기

`/sync`(Claude Code) 또는 `node scripts/sync-fingerprint.mjs`가 각 레포의 기준 브랜치를 읽어 지문을 만들고 이전 baseline과 비교한다. 스택 버전·명령·포트·구조 같은 사실은 그대로 반영하고, 판단이 들어간 문장은 "확인 필요"로 남긴다. 갱신 후 `--accept`로 baseline을 확정한다.

레포가 아니라 **이 워크스페이스 자체**의 구조가 바뀌면(에이전트·스킬 추가 등) `docs/extending.md`를 따른다. sync는 그 변화를 잡지 않는다.

외부 가이드라인(공개 CLAUDE.md·스킬·플러그인 등)은 통째로 설치하거나 덧붙이지 않는다. 기존 규칙과의 중복·충돌·적용 범위를 검토해 필요한 것만 기존 정본 문서에 한국어로 통합한다.
