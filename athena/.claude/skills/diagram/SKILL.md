# 서비스 다이어그램

Claude는 `/diagram`, Codex는 `$diagram`으로 같은 정본을 읽는다. 인자는 사용자가 쓴 텍스트를 읽고 `$ARGUMENTS`가 치환되지 않았으면 그대로 명령에 넘기지 않는다.

먼저 `docs/diagrams/AUTHORING.md`를 읽는다. 서비스는 현재 팩 `pack/diagrams/SERVICES.md`와 `pack/pack.json`의 레포·앱에서 고른다. 기준 ref는 `branch`이며 `prBase`가 아니다. 서비스 표가 없으면 팩의 레포·앱에서 확인한 목록을 만든다. 회사 이름·개수를 고정하지 않는다. 이름이 여러 서비스와 겹치면 대상을 확인한다. 인자가 없으면 현재 팩 전체이며 대상과 예상 범위를 먼저 알린다.

- **점검**: `node scripts/check-diagrams.mjs --strict --design`로 고정 근거·운영 ref 차이와 공통 테마·최종 브라우저 증거를 보고한다. 대상만 요청받았어도 도구 출력의 전체 결과와 대상 결과를 구분한다. 스펙·HTML·revision을 자동으로 고치지 않는다. Archify 검증·브라우저 확인 여부도 따로 보고한다.
- **생성·갱신**: 기존 가이드 `pack/diagrams/guides/<서비스>.md`를 읽고, 해당 운영 ref의 격리 체크아웃을 사용한다. 현재 `archify` 스킬의 SKILL.md·선택한 schema·예제를 읽고 JSON → validate → 원본 deliver → 아테나 공통 테마 최종본 → 최종본 visual-check 절차를 따른다. 실제 화면·기능·모듈·API·저장소·외부 연동을 목록화하고 가이드에 각 항목이 들어간 장·상자 또는 제외 근거를 기록한다. **서비스마다 '한눈에 보기' 1장 + 핵심 기능 흐름 2~3장, 모두 3~4장**이다. 핵심 흐름은 사용자가 가장 자주 쓰는 기능과 실패하면 가장 아픈 기능에서 고르고, 나머지 기능은 한눈에 보기의 상자와 그 자세히 칸에 넣는다. 코드 위치·수정 영향은 별도 장(수정 영향·화면 맵·○○ 연결 등)으로 만들지 않고 모두 자세히 칸에 넣는다. 구체적인 기준은 AUTHORING "내용 — 한눈에 보기 + 핵심 흐름"을 따른다. 파일 이름은 기존 것을 재사용한다 — 한눈에 보기 `<서비스>.html`, 흐름 `<서비스>.<기능>.sequence.html`(기존 `<서비스>.sequence.html`이 핵심 흐름이면 그대로). 기준에서 빠지는 기존 장은 index에서 내린다(AUTHORING "점검·목록"). 옛 번들·QA 실행 체계는 복원하지 않는다.
- **처음 보는 사람 · 자세히 칸**: AUTHORING "처음 보는 사람 기준" 을 따른다 — 첫 줄 한 문장 요약 · 사람이 보는 상자 이름 · 단추에서 결과까지 · ①②③ 묶음 · 실패 단계 바로 아래 줄의 실제 화면 문구 · `meta.legend.entries` 의 쉬운 말 범례. 그림과 함께 최종 HTML 옆에 `<최종 이름>.details.json` 을 만든다 — 상자마다 하는 일(`what`) · 코드 위치(`code`) · 변경 영향 범위(`impact` — 개발자용 칸이니 호출부 · 응답 스키마 · 의존 모듈 · 소비처 같은 개발 용어로 쓴다) · 확인할 테스트(`tests`). 쓰기 전에 **줄 번호마다 격리 체크아웃의 그 파일을 다시 열어** 그 줄이 맞는지 확인한다. 확인하지 못한 것은 넣지 않고 가이드에 "확인 못 함" 으로 남긴다. 테마 단계(`diagram-theme.mjs --output`)가 이 파일을 함께 넣고, 그림에 없는 상자 id 면 실패한다.
- **공통 디자인·전달**: `scripts/diagram-theme.css`·`.mjs`와 기존 아테나 작업 흐름 그림이 디자인 정본이다. AUTHORING의 `--output` 절차로 Archify 원본과 테마 최종본을 분리하고 해시·영수증을 대조한다. 원본 deliver 합격을 최종본 합격으로 쓰지 않는다. 최종본에서 작은/큰 데스크톱·밝음/어두움 브라우저 증거와 실제 시각 검토를 새로 수집한다. 실패한 deliver의 이전 HTML이나 stale 캡처로 성공을 보고하지 않는다.
- **서버 그림**: 팩 `pack.json` `servers[]` 의 서버는 AUTHORING "서버 그림 — 팩 `servers`" 를 따른다 — 서버마다 한눈에 보기 1장(`server-<이름>.html`) · 근거는 `scripts/ssh-run.sh <이름> -- …` 허용 목록 읽기 명령의 결과와 `docs/knowledge/servers/<이름>/` · 주소 · 사용자 · 키 · 환경 값은 넣지 않는다. 인자가 서버 이름이면 그 서버만, 인자가 없으면 서비스와 서버 모두가 대상이다.
- 결과와 가이드는 **현재 팩 `pack/diagrams/`**에 쓴다. 본체 코어의 회사별 파일을 만들지 않는다. Archify가 없으면 설치 여부를 보고하고 멈춘다(전역 자동 설치·개인 스킬 수정 금지).
- 구조 그림은 `meta.repository`와 실제 `components[].sources`를 넣고 `--repo-root <격리 체크아웃>`으로 검증·전달한다. sequence 등은 이 옵션을 받지 않으므로 가이드에 코드 근거·고정 커밋을 기록한다. 근거를 확인할 수 없으면 그 장만 멈추고 미확인으로 남긴다.
- 검증된 HTML만 `pack/diagrams/index.json`의 카드에 등록하고 `node scripts/build-diagram-index.mjs`로 목록을 갱신한다. 필요하면 `bin/athena pack link`로 가이드·그림 링크를 맞춘다. 메뉴 목적지는 기존 `docs/diagrams/index.html`이다.

현재 프로젝트의 계획서·검증·커밋·PR 흐름을 따른다. 코드·knowledge를 그림 생성 중에 임의로 고치지 않는다. 보고에는 서비스별 고정 ref·산출물·검증·브라우저 증거·시각 검토·미확인을 구분하고 계획서에 기록한다. 실제 서비스 전체 재생성은 사용자가 요청한 범위에서만 한다.

새 단일 레포의 서비스 ID는 `<레포>`, 새 모노레포 앱은 `<레포>/<앱>`이다. 예를 들어 `one/web`과 `two/web`은 서로 다른 폴더의 JSON·HTML·가이드와 카드 base를 사용한다. 기존 팩의 서비스 ID·파일은 그대로 재사용하며 동명 앱이 추가되면 레포까지 지정해 구분한다.
