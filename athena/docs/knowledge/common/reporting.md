# 팀 공통 보고 규칙

에이전트 완료 보고는 항상 아래 4항목 — 사용자가 먼저 알고 싶은 것부터, 쉬운 말로 짧게. 아테나는 이걸 취합해 사용자에게 전달한다. 보고 전에 계획서 Checkpoint(Progress·결과)를 갱신한다 — **안 써도 되는 칸**: Validation 줄은 검증 스크립트가, 커밋 뒤 Status `ready_for_review` 는 `commit.sh` 가 적는다(커밋 없이 끝나면 Status 는 직접 · `docs/workflow.md` 4절).

1. **무엇이 달라졌나** — 계획서 항목별 완료 / 미완료 / 다르게 한 것과 이유
2. **어디서 확인하나** — 화면 주소(로컬·dev)·PR·바뀐 파일(경로, 레포/앱/레이어별)
3. **검증 결과** — 검증 스크립트가 계획서 Validation 에 한 줄을 적으니, 보고에 출력 표와 결과(실패는 원문)를 옮긴다. 실패는 원문 포함. **실행하지 못한 검증은 "실행 못 함"이라고 적는다** (통과한 것처럼 쓰지 않는다). 커밋했다면 `commit.sh` 가 계획서 `## Commits` 에 적은 SHA 를 함께 적고, push·PR 을 했으면(`ship.sh`) PR 링크를, 안 했으면 안 했음을 밝힌다
4. **남은 일·위험** — 사용자가 해야 할 것(로그인·인증·키 입력 등 — 있으면 맨 위), 확인 못 해 멈춘 것(무엇을 모르는지 · 확인에 필요한 것), 범위 밖 수정 필요, 다른 서비스 영향, 후속 작업. 그 자리에서 고치지 않은 것은 `docs/issues.md` "등록 기준"대로 — 보안·버그(high)는 `issues/<YYYYMMDD>-<레포>-<제목>.md` 로 바로 등록하고 경로를 적고, 나머지는 "이슈 후보"로 적어 사용자가 고르게 한다 — 지금 작업 중인 계획서 경로는 `plan:` 이 아니라 `source:` 에 적는다(`plan:` 은 그 이슈를 고치는 계획서다)(형식 `docs/issues.md`)

보고 다음에 — **넓은 수정(새 기능 · 구조 변경 · 여러 파일에 걸친 로직 변경 · 보안 · 권한 · 데이터 · 외부 계약에 닿는 코드)이면** 정식 계획서(여러 레포 작업 포함)는 **묻지 않고 바로 리뷰를 띄우고**(자동 리뷰), 경량 계획서(`plans/task/`)는 보고 끝에 "리뷰할까요?" 한 줄만 붙여 사용자가 "리뷰해줘" 할 때 띄운다. 리뷰 지적 반영 · 문구 · 문서 · 작은 수정이면 띄우지도 묻지도 않는다(2026-10-25). 띄우는 법은 같다: `scripts/delegate.sh reviewer --cwd <워크트리> --here --plan <계획서>` 로 옆에 reviewer pane. 결론(`- Review result:`)이 나오면 사용자에게 보여 준다. reviewer 보고에 **결정 필요**(조사한 뒤에도 사용자가 정해야 하는 것 — 범위·사용자 동작·외부 계약·제품 정책·데이터)가 있으면 말로 묻지 않고 **결정 콘솔**로 — 같은 계획서에 `## 리뷰 뒤 결정` 절을 적고 `node scripts/plan-html.mjs <계획서> --add <결정.json>` → `scripts/board.sh open <계획서>`. 사용자가 고르고 [이대로 진행] 하면 이 pane 으로 결정이 온다. 대화로 "추천대로"·"R1 은 B"처럼 답해도 같다 — 계획서·콘솔에 확정을 기록하고 진행하며, 콘솔을 다시 누르라고 하지 않는다. 수정 필요(고칠 방법이 하나)는 묻지 않고 고친 뒤 무엇을 고쳤는지 한 줄씩 알린다. 조사만 했거나 마지막 리뷰 승인 뒤 바뀐 게 없으면 띄우지 않는다

원칙:
- 승인된 범위 안의 후속 일(리뷰 반영·재검증·다른 pane 에 전달·Status 갱신)은 사용자에게 되넘기지 않고 끝낸다. 다른 pane(아테나 포함)에 넘길 일은 `scripts/screen pane send-text <pane> '[<나> → <받는 쪽>] …' --enter` 로 직접 보낸다 — "전달해 주세요"라고 하지 않는다. 아테나 pane 으로 보내기가 실패하면(명령 실패 · 훅 차단 · 아테나 pane 없음) 우회하지 말고 보낼 글을 계획서 Checkpoint(Blocked 또는 결과 절)에 그대로 적고 `bin/athena request open --kind question --title '<한 줄>' --body-file <파일> --plan <계획서>` 로 요청을 열어 현황판에 뜨게 한 뒤, 보고 끝에 그랬다고 한 줄 적는다
- 결정·선택지는 번호만 던지지 않고 무엇을 정하는지·고르면 무엇이 달라지는지 한 줄씩 붙인다. 시키지 않은 화면 문구·기능을 덧붙이지 않는다
- 로그인·본인인증·키 입력처럼 사람이 해야 하는 단계에서는 넘기거나 계속 도는 척하지 않고 멈춰서 무엇을 어디서 할지 알린다
- 추측으로 구현하지 않는다 — 코드만 보고는 알 수 없는 사실은 코드·실행·문서로 확인하고, 그래도 모르면 그 부분만 멈추고 계획서 Blocked 에 적은 뒤 모르는 것을 모아 한 번에 묻는다(무엇을 모르는지 · 어디까지 확인했는지 · 필요한 것 · 추천안 — `AGENTS.md` 5절). 평범한 구현 선택은 묻지 않는다. 추천안은 확인한 사실 위에서만 세운다 — "추천대로"는 선택을 정할 뿐 사실을 확인해 주지 않는다. 보고에 "추측으로 처리한 부분"이 생기면 그 자체가 규칙 위반이다
- 확인하지 못한 내용은 사실처럼 쓰지 않고 "확인 못 함"이라고 명시
- 내 명령 뒤에 예상 못 한 종료(시뮬레이터 · 서버 · 앱)를 보면 다시 켜기 전에 원인부터 확인하고 보고에 적는다 — 내가 낸 명령이 원인일 수 있다
- 한국어로 소통, 코드 주석도 한국어. 영어는 코드·파일명·기술 용어만
- 같은 오류 3회 반복, 범위 밖 수정 필요, 규칙 충돌은 진행하지 말고 보고
