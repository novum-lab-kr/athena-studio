어떻게 꺼내 쓰나 — "결제 페이지 프로모션 배너 고쳐줘"라고 하면 ① 팩 라우팅 규칙(pack/ROUTING.md)으로 레포·에이전트를 고르고(갈리면 되묻습니다) ② structure.md 화면 지도 → 실제 코드 → 화면 문구 검색으로 파일을 찾고(후보가 여럿이면 되묻습니다) ③ 그 경로를 계획서에 적어 담당 에이전트에게 맡깁니다. 에이전트는 시작 전에 그 레포의 rules.md 필수 절과 gotchas.md 를 전부 읽습니다. 문서와 코드가 다르면 코드를 믿습니다 — 노트는 길잡이이고 정답은 지금 코드입니다.

언제 최신이 되나 — /sync 가 운영에 배포된 코드(팩 pack.json 의 레포별 branch)를 읽어 지난번 이후 바뀐 것만 반영합니다. 자동으로 돌지 않고 누군가 돌릴 때만이며, 확인되는 사실(새 화면·버전·명령)만 고치고 판단이 필요한 문장은 "확인 필요" 이슈로 묻습니다. 그래서 아직 배포 안 된 화면은 노트에 없고, 작업할 때 코드에서 직접 찾습니다.

아테나가 혼자서는 알 수 없는 것 — 사람이 채워 줍니다. 화면의 업무 용도("이 페이지는 영업팀이 제휴사 고객 번호를 한꺼번에 조회할 때 쓴다"), 어느 팀이 쓰는지·언제 쓰면 안 되는지 같은 코드 밖의 운영 규칙은 코드에 없습니다. 아테나에게 "○○ 페이지는 △△ 용도야. 지식 문서에 적어줘"라고 하면 structure.md 화면 설명에 "사용자 확인" 표시와 함께 들어가고, 커밋하면 팀 전체가 압니다. 학습 기능은 근거가 "사용자가 말했다"뿐인 후보를 취향일 수 있다고 보고 거르므로, 업무 지식은 이렇게 직접 적어 달라고 하는 게 확실합니다.

담당 레포의 운영 기준 브랜치를 fetch 해 지식 문서·에이전트 md·서비스 맵·팩 판 플레이북을 운영에 반영된 상태에 맞게 고칩니다. 로컬 작업 트리는 브랜치가 제각각이라 읽지 않고, 항상 아래 origin/<기준 브랜치> 를 봅니다. 이전 sync 이후 바뀐 부분만 찾아 반영합니다.

예: 모노레포 공통 packages/* (앱들이 공유)origin/devdev

문서 기준 커밋

지식 노트와 에이전트 md 의 스택·포트·구조 정보는 레포마다 운영 반영분(팩 pack.json 의 레포별 branch) 커밋을 읽어 만든 것입니다. 어느 커밋을 기준으로 삼았는지는 회사마다 다르므로 코어판에는 표가 없습니다.

레포별 기준 커밋 표는 팩 판 플레이북(팩 guide/playbook.html)에 있습니다. /sync 가 지문을 확정하면 scripts/build-derived.mjs 가 그 표와 헤더의 last sync 를 채웁니다. 레포의 운영 브랜치가 표보다 앞서 있으면 /sync를 돌려야 문서가 따라옵니다.

작업 흐름

아테나는 요청마다 경량인지 정식인지 먼저 정해 한 줄로 알립니다. 대부분인 경량(레포 하나 · 문구 · 버그 하나 · 조사 · /call)은 계획서를 자동으로 기록만 하고 승인 단계 없이 에이전트 pane 에서 커밋·리뷰·PR 까지 갑니다. 정식(여러 레포·API·구조 변경)만 아래 6단계를 모두 거칩니다. 어느 쪽이든 모든 작업은 계획서 하나에 묶입니다. 그림은 /guide 그림 의 작업 흐름 · 경량, 작업 흐름 · 정식 두 장입니다. 진행 상황은 현황판(/board)에서 실시간으로 봅니다. 원본은 CLAUDE.md "작업 흐름"입니다.

아테나
  • 요청은 세 갈래로 들어옵니다 — 대화(담당자를 모르거나 여러 레포·기능·버그 원인 찾기), /call <에이전트>(담당자를 알 때), 현황판 이슈 카드의 [작업 시작].

사용자

0인 항목은 표시하지 않습니다. athena 워크스페이스(코어) 자체는 main 이 정상 작업 브랜치라 보호 브랜치 경고에서 제외됩니다.

설정은 레포에 들어 있습니다. .claude/settings.json 의 statusLine 과 scripts/statusline.sh 가 함께 커밋되므로, clone 하면 바로 같은 상태바가 뜹니다. 대상 레포는 scripts/delegate.sh 가 팩 pack.json 에서 찾아 넘겨줍니다. 다만 이 프로젝트 안에서는 개인 전역 statusLine 설정을 덮습니다.

작업 · 커밋 (pane 에서 반복)

FE 에이전트
  • 사용자가 pane 에서 여러 번 요청합니다. 요청마다 Status 가 in_progress ↔ ready_for_review 로 바뀌어 현황판 카드가 진행 중 ↔ 리뷰를 오갑니다.
  • 작업 뒤 표준 검증 스크립트(scripts/verify/*.sh)를 돌리고 출력 표를 그대로 보고합니다.
  • 커밋은 사용자가 "커밋해줘"라고 할 때만 scripts/commit.sh로 합니다 — 지정 파일만·엄격 검증·계획서 ## Commits 기록. 메인 체크아웃·보호 브랜치·검증 실패면 거부합니다.
  • 레포 하나짜리 작업은 여기서 PR 까지 — 코드를 바꾼 요청을 보고하면 정식 계획서는 에이전트가 묻지 않고 바로 옆에 reviewer pane 을 띄우고(자동 리뷰), 경량 계획서(/call 포함)는 보고 끝에 "리뷰할까요?" 한 줄만 붙여 "리뷰해줘" 할 때 띄웁니다. 리뷰어는 같은 트리로 이미 통과한 검증을 다시 돌리지 않습니다(♻️ 재사용). 결론이 나오면 보여 주고, 수정 필요(고칠 방법이 하나)면 묻지 않고 고친 뒤 무엇을 고쳤는지 알려 줍니다. "리뷰해줘"로 다시 받을 수도 있고, "PR 올려줘"면 scripts/ship.sh 가 base 후보·올라갈 커밋·검증·리뷰 기록·제목 제안·본문 초안을 보여 준 뒤 확인받아 draft PR 을 엽니다. 커밋 안 된 변경, commit.sh 를 안 거친 커밋, 여러 레포 작업, 형식에 안 맞는 제목은 거부합니다.

검증 · 보고 · push/PR

reviewer · 아테나
  • 여러 레포 작업이나 아테나가 맡은 작업은 아테나에게 "리뷰해줘" — reviewer 가 계획서와 워크트리를 받아 diff를 읽고 검증 스크립트를 다시 돌려 에이전트 보고와 비교합니다. 수정 필요 항목은 사용자 확인 뒤 그 FE pane 에서 이어서 지시합니다.
  • 서비스별 변경 파일·주요 변경·검증 결과·## Commits·남은 위험을 요약합니다. 검증 실패는 숨기지 않습니다.
  • 여러 레포에 걸친 작업의 push·PR 은 아테나가 순서(공유 패키지 먼저)·공개 범위를 확인하고 사용자에게 물은 뒤 레포마다 ship.sh --repo-agent 로 올립니다. 레포 하나짜리는 에이전트 pane 에서 올립니다(4단계).

정리

아테나
  • 끝난 카드는 현황판 완료 칸의 [아카이브] — 이슈와 계획서를 archive/<이름>/ 한 폴더로 묶어 보관하고 git 에 커밋합니다. git 에 올라가는 건 이 archive/ 뿐이고, 진행 중·리뷰·완료의 이슈·계획서는 각자 로컬에 갖습니다. 이슈 워크트리도 정리합니다(미커밋·push 안 된 커밋이 있으면 남김). 지나간 일은 현황판 [아카이브] 탭에서 검색합니다.
  • 계획서 PR: 줄의 PR 이 모두 머지되면(어느 base 든 — GitHub MERGED) 현황판이 그 계획서를 자동으로 완료로 옮깁니다(진행 중·리뷰 계획서만, 5분마다 확인 · 완료된 계획서에 이어 PR 을 올리면 자동 머지를 켠 레포는 리뷰로 되돌려 자동 리뷰를 다시 태웁니다). 머지 없이 닫힌 PR(CLOSED)은 셈에서 빼고, 그것만 있으면 옮기지 않습니다.
  • 이슈는 완료 기준이 채워지면 완료 가능 배지가 붙고 아테나가 완료로 옮깁니다. 안전망: scripts/archive-plans.sh(30일 이상 + 최근 git log 미언급).
  • 📚 학습 — 에이전트는 작업을 끝낼 때(PR 을 올린 보고)·사용자가 바로잡을 때·같은 오류가 3번 날 때 "다음에도 밟을 코드 함정"을 학습 후보로 올리고, PR 이 머지되면 배우기 검토자(별도 Claude, 뒤에서 돈다)가 계획서·대화·바뀐 코드·리뷰 댓글을 읽어 보탭니다. 사용자가 현황판 [학습] 탭에서 [넣기]를 고른 것만 서비스별 공책(gotchas.md)에 들어가고, 다음 작업이 읽습니다. 일하는 취향은 넣지 않습니다(근거가 코드·실행 결과일 때만). 기준 docs/knowledge/common/learning.md

규칙

규칙은 세 층입니다. 팀 공통(docs/knowledge/common/: 코드·Git·보고) → 레포 규칙(docs/knowledge/<레포>/rules.md: 공통과 다른 점) → 레포 원문(레포 안 CLAUDE.md·AGENTS.md·규칙 문서 등). 충돌하면 뒤가 우선합니다. 아래는 아테나 자신의 운영 규칙 요약입니다 — 늘 실리는 것은 AGENTS.md(공통) · CLAUDE.md(아테나) · .claude/rules/coding-standards.md(코드) 셋이고, 자세한 절차는 필요할 때 읽는 docs/ 문서로 나눴습니다(2026-10-29).

Git (AGENTS.md 5절)

  • FE 에이전트는 사용자가 pane 에서 "커밋해줘" · "PR 올려줘" 라고 할 때만 scripts/commit.sh 로 로컬 커밋(지정 파일만·엄격 검증·계획서 기록). push·PR 은 "PR 올려줘" 일 때 scripts/ship.sh 로 — 그 한 마디로 커밋 → 제목·본문 정리 → 묻지 않고 draft(레포 하나짜리)
  • PR 제목 type(범위): 티켓 요약 · 본문 공통 템플릿 (git.md "PR 제목·본문")
  • 시작 전 git status로 기존 변경 확인, 무관한 파일은 건드리지 않음
  • 커밋 메시지는 한국어, 티켓 있으면 feat: PROJ-1234 설명

코드 (.claude/rules/coding-standards.md)

  • 기존 패턴 분석 후 그 패턴을 따름
  • 범위 밖 정리·의존성 업그레이드·파일 이동·전역 포맷팅 금지
  • 1글자 변수명, 3항 중첩, 새 코드의 any 금지
  • 요청 안 한 범용화·옵션·prop 금지. 필요한 분리와 상태·오류·보안 처리는 유지
  • 이번 변경으로 생긴 미사용 코드만 정리, 기존 것은 보고·이슈 등록
  • 같은 오류 3회 반복 시 접근 재검토 후 보고

디스패치 (docs/dispatch.md)

  • 계획서(정식은 승인 후 · 경량은 지시가 곧 승인)가 있어야 디스패치 — delegate.sh --plan 필수
  • 독립 작업은 한 응답에서 동시 호출
  • 결과 보고에서 변경 파일·검증 결과·남은 위험 확인

언어 (AGENTS.md 6절)

  • 한국어로 소통, 주석도 한국어
  • 영어는 코드·파일명·기술 용어만
  • 확인 못 한 것은 "확인 못 함"이라고 명시(추측으로 구현하지 않음)

확장하기

스킬(슬래시 커맨드)과 에이전트는 파일 하나로 추가됩니다. 추가한 뒤에는 문서 몇 곳을 같이 손봐야 합니다. 같은 내용이 docs/extending.md에 있고, 터미널에서 /guide로 바로 볼 수 있습니다.

스킬 추가

  • .claude/skills/<이름>/SKILL.md 하나 만들면 /<이름>으로 바로 뜹니다
  • frontmatter에 name, description, 필요하면 argument-hint를 둡니다
  • 본문에서 $ARGUMENTS로 인자를 받습니다
  • 기존 call/SKILL.md를 복사해서 고치는 게 가장 빠릅니다

에이전트 추가

  • .claude/agents/<이름>.md 하나 만들면 됩니다
  • frontmatter의 description은 아테나가 라우팅할 때 읽는 문장입니다. "어떤 요청이면 이 에이전트"를 구체적으로 적어주세요
  • description 안에 콜론+공백(: )이 들어가면 YAML이 깨집니다

같이 갱신할 곳

  • CLAUDE.md의 서브에이전트 줄·Skills 줄 (설명은 docs/workflow.md "명령" 표)
  • README.md
  • docs/playbook.html (이 문서)
/sync는 레포 쪽 변화만 반영하고 athena 자체 구조 변화는 잡지 않습니다. 스킬이나 에이전트를 추가했으면 아테나에게 "방금 추가한 스킬 문서에도 반영해줘"라고 하면 위 세 곳을 갱신합니다.

자주 묻는 질문

슬래시 커맨드를 꼭 써야 하나요?
아니요. "주문 목록에 검색 추가해줘"처럼 말하면 CLAUDE.md 규칙에 따라 아테나가 같은 흐름으로 움직입니다. 커맨드는 흐름을 확실히 타게 하는 단축키입니다.
에이전트를 직접 지정할 수 있나요?
가능합니다. "<에이전트>로 주문 목록 화면에 컬럼 하나 추가해줘"라고 하면 아테나가 그 에이전트에 넘깁니다. 단, 계획서를 건너뛸지는 아테나가 작업 크기를 보고 판단하며, 규모가 있으면 계획서를 먼저 씁니다.
아테나는 스스로 배우나요?

네, 다만 사람이 고른 것만 배웁니다. 작업에서 알게 된 코드 함정이 서비스별 공책(gotchas.md)에 쌓이고, 에이전트는 작업 전에 이 공책을 읽습니다.

누가 — ① 작업한 에이전트가 작업을 끝낼 때(PR 을 올린 보고)·사용자가 바로잡을 때·같은 오류가 3번 날 때 학습 후보를 올리고 ② 배우기 검토자(별도 Claude)가 PR 이 머지된 뒤 계획서·대화·바뀐 코드·리뷰 댓글를 다시 읽어 빠진 것을 보탭니다 ③ 사람이 현황판 [학습] 탭에서 [넣기]·[고쳐서 넣기]·[버리기] — 넣은 것만 공책에 들어갑니다.

기준 — 다시 마주치고 · 모르면 실제로 잘못되고 · 코드만 봐서는 바로 알기 어려운 것만. 근거가 코드나 실행 결과로 확인돼야 하고, "사용자가 그렇게 말했다"뿐이면 취향일 수 있어 스크립트가 거릅니다(취향은 각자 Claude 메모리 몫). 이미 코드로 고친 버그·한 번 있었던 일·원인이 서버인 것은 넣지 않습니다. 대부분의 작업은 0개가 정상입니다. 정본 docs/knowledge/common/learning.md.

누가 배우나배우기 전용 에이전트가 뒤에서작업한 에이전트 + 배우기 검토자, 최종은 사람
언제대화 10번·도구 10번마다 자동작업 끝 · 사용자 교정 · 같은 오류 3회 · PR 머지 뒤(리뷰 댓글까지)
저장바로 저장(사람 확인 없음)[넣기]를 누른 것만
무엇을스킬·기억레포 함정(공책). 반복 절차는 "스킬로 만들까요?"라고 묻는다
취향같이 기억공용 공책엔 안 넣고 각자 Claude 메모리로
근거 확인LLM 이 판단코드·실행 결과로 확인된 것만(스크립트가 거른다)
공유내 컴퓨터git 으로 팀 전체
지난 대화 검색있음없음

왜 사람이 승인하나 — 공책은 모든 작업이 매번 다 읽는 팀 공용 문서라, 잘못 배운 한 줄의 비용이 큽니다. 넣기·버리기 비율을 세고 있어서, 믿을 만하다는 숫자가 나오면 자동으로 넣는 쪽으로 다시 정할 수 있습니다.

급한 수정은 어떻게 하나요?
"바로 고쳐"라고 명시하면 결정 콘솔 단계를 건너뛰고 경량 계획서(plans/task/…, 사용자 지시가 곧 승인)로 바로 디스패치합니다. 계획서 없이 디스패치하는 예외는 없습니다. reviewer 검증은 그대로 진행합니다.
백엔드 API가 아직 없는데 화면부터 만들 수 있나요?
계획서의 "API 의존성" 항목에 필요한 엔드포인트와 응답 타입을 적고, 백엔드가 준비될 때까지의 처리 방식(임시 훅 / mock / 대기)을 결정합니다. 레포마다 임시 처리 방식이 다르면 그 레포 지식(docs/knowledge/<레포>/)에 적어 두고, 에이전트는 임시로 만든 것을 보고에 명시합니다.
공유 패키지(사내 발행 패키지 등)를 고쳐야 하면요?
FE 에이전트는 직접 고치지 않고 아테나에 보고합니다. 아테나는 이를 "외부 의존"으로 사용자에게 알리고, 패키지 레포 작업을 먼저 끝낸 뒤 소비 레포로 넘깁니다(패키지를 담당하는 에이전트가 없으면 별도로 진행합니다).
레포가 바뀌면 에이전트 문서는 누가 고치나요?
/sync를 치면 아테나가 담당 레포의 운영 기준 브랜치(팩 pack.json 의 레포별 branch, 모노레포는 앱별 — /sync 카드)를 읽어 바뀐 사실(버전·명령·포트·구조·포맷·규칙 문서)만 골라 문서를 고칩니다. 자동으로 상시 감시하지는 않으니, 세션을 시작할 때 문서가 오래된 것 같으면 한 번 돌려주세요. 판단이 들어간 문장은 자동으로 바꾸지 않고 "확인 필요"로 알려줍니다.
reviewer는 왜 따로 있나요?
작업한 에이전트가 자기 코드를 검증하면 놓치는 부분이 있습니다. reviewer는 읽기 전용으로 계획서 대비 누락·초과, 레포 규칙 준수, 여러 서비스에 같은 기능을 넣었을 때의 문구·동작·env 키 일관성을 봅니다. 필요 없으면 .claude/agents/reviewer.md 하나만 지우면 됩니다.
